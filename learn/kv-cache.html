TRANSFORMER INFERENCE · KV CACHE

KV Cache 如何加速解码，又占多少显存？

为什么历史 token 的 K 和 V 可以复用#

假设一个仅解码器 Transformer 已读完输入，现在要接着生成下一个 token。自注意力会用当前位置的 Query（Q）和可见位置的 Key（K）算匹配分数，再按权重读这些位置的 Value（V）。公式和一个具体的加权计算可接着看 Softmax 与 Attention。

因为因果掩码只允许每个位置读取它自己和更早的位置，追加一个 token 时，旧位置看不到新内容。在同一次推理中，模型权重、位置编码和旧前缀固定，旧位置在每层的 K 和 V 就可以沿用。KV Cache 存的是这些逐层累积的张量。下一步需要的是新 token 的 Q，旧位置的 Q 已经用完了。[1]

把一次生成拆成预填充和解码#

用 A、B、C 表示三个输入 token，D、E、F 表示依次采样出的 token。预填充（prefill）用整段输入填好每层的 K、V，并从最后一个位置得到预测 D 的概率。解码（decode）再把刚选出的 D 送入模型，借助已有缓存推算 E。

三个输入 token 的生成示例
阶段本轮输入本轮写入 K/V本轮输出
预填充A、B、CA、B、C采样 D
解码 1D追加 D采样 E
解码 2E追加 E采样 F

第一步解码用 Q_D 查询 [K_A, K_B, K_C, K_D]，再对对应的 V 做加权。此时缓存长度为 4。下一步输入 E 后才把 E 的 K 和 V 放进缓存，所以刚采样出的 F 要等到下一轮前向才会入缓存。[1]

少算的是旧位置，新增位置仍要读历史#

以第一步解码为例。朴素做法会重新输入 A、B、C、D，重复计算旧位置的投影、注意力和后续层。缓存方式只为 D 执行各层的前向，并读出先前存好的 A、B、C 的 K 和 V。在这一层，查询与键的计算形状从 4×4 缩到 1×4。

令 S 是本轮可见的 token 数。固定模型宽度，按普通全注意力的计算量估算，每步重算整个前缀的注意力是 O(S²)，而缓存后的单 token 解码只算一行，是 O(S)。首次预填充仍要处理完整的输入，后续解码也要逐步读取变长的 K/V。长上下文时，缓存读写会占用更多内存带宽，实际时延还取决于批量大小、内核实现和硬件。

从模型参数估算 KV Cache 显存#

先算标准全长缓存的原始张量大小。同一批次内各序列都长 S 时，乘上并发序列数 B、层数 L、每层 KV 头数 H、每个头的维度 D，以及单个数值的字节数。乘 2 是因为 K 和 V 分别存一份。

KV 字节数 = B × S × L × 2 × H × D × 单个数值的字节数

以 32 层、8 个 KV 头、头维度 128、BF16（2 字节）为例，每个 token 的缓存是 128 KiB。单条序列缓存 8,192 token 时是 1 GiB，到 32,768 token 时是 4 GiB。四条同样长的 8,192-token 序列合计也是 4 GiB。长度各异时，把每条序列的有效缓存长度相加。实际显存还包括模型权重、临时工作区、分配粒度和框架开销。

KV Cache 显存计算器32 层 · 头维度 128 · BF16

原始缓存 1.00 GiB

在 GQA（分组查询注意力）里，一组查询头共享一个 KV 头。一个有 32 个查询头、8 个 KV 头的模型，用 8 代入公式。假设其他参数相同，它的原始 KV 张量是 32 个 KV 头的模型的四分之一。[2]

前缀缓存和分页分别优化哪一步#

在推理服务里，单次生成已经能复用自身的历史。如果多个请求反复提交同一段长文档，前缀缓存还能复用已命中的前缀块，省掉这段前缀的重复预填充。匹配依据包括 token 序列及其前序块。把同一份文档放在同样的提示前缀里，后面再接不同的问题，前面的完整块就有机会复用。[4]

并发请求的上下文长短不同，缓存也随解码逐步增长。PagedAttention 将一条序列的 K/V 按固定长度的块管理，按需分配，允许块在物理内存中不连续。它处理的是缓存的分配和碎片，GQA 改变的是模型每个 token 要存多少个 KV 头，两者可以组合。[3]

用计算器做个小练习。先把长度从 8,192 调到 32,768，再把长度调回 8,192、把并发调成 4。两种情况下原始张量都变成 4 GiB，但前者每条序列要读更长的历史，后者要同时服务更多序列。容量公式适合先估显存，吞吐和延迟仍要按实际服务形态测量。

核心机制Softmax 与 Attention 原理：公式、计算与注意力稀释 ↗

Attention 决定从前文各处取多少信息，Softmax 负责把分数换成比例。从 Q、K、V 的含义开始，逐步算出这些比例，再说明内容变多时，为什么一条信息分到的比例可能变小。

核心机制ReAct 框架原理 ↗

AI 先决定下一步，再用工具查资料或做事；拿到工具返回的结果后，继续决定做什么。这篇解释 Thought、Action、Observation，以及它们怎样连成一个循环。

核心机制Agent Loop 原理 ↗

Agent Loop 是让 AI 持续做完任务的程序循环。它记录任务做到哪一步，调用模型和工具，并决定继续、等待、停止，或在中断后接着做。

核心机制Supervisor、Verify 与 Eval：职责、机制与对比 ↗

Supervisor 决定下一步做什么，Verify 检查眼前的结果是否符合要求，Eval 记录并比较任务做得怎样。这篇说明三者怎样配合，以及漏检和误拦怎样计算。

核心机制工具调用（Tool Calling）原理 ↗

AI 给出要用的工具和参数，应用实际执行，再把结果交回 AI。这篇解释工具定义、参数格式、调用编号，以及请求与结果怎样一一对应。

核心机制Workflow 与 Agent ↗

Workflow 先在程序里写好处理顺序和分支；Agent 让 AI 根据工具结果决定接下来做什么。两者都能使用模型和工具，差别是谁选择下一步、能改多少步骤。

上下文与协作上下文工程原理 ↗

上下文工程决定每次给模型看什么：选出相关资料，分清事实和猜测，保留任务进度，并及时更新已经过时的内容。

上下文与协作Agent 规划与反思原理 ↗

规划说明先做什么、后做什么；反思回看执行结果，提出下一次改法。真正的改进需要把改法用到行动中，再检查结果。

上下文与协作多 Agent 协作原理 ↗

多 Agent 协作把任务分给几个 Agent，再交换结果并合到一起。要能真正完成任务，需要分清谁负责什么、彼此传什么，以及最后由谁检查整体结果。

上下文与协作MCP 协议原理 ↗

MCP 约定 AI 应用与外部工具怎样交流。应用先取得工具说明，再发送调用请求、接收结果；负责应用、负责通信和提供工具的程序各有分工。

按事先定好的条件，检查 AI 是否把事办成、做事时是否守规矩，以及换一次运行还能不能成功。结合 ACL 2026 综述解释常见做法。
